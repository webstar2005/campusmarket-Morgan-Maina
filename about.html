The project

About this build

CampusMarket is one running project for the whole semester. Each week adds one layer to the same app, so nothing is thrown away at the end of a topic.

What CampusMarket is

A marketplace where students buy and sell second-hand items to each other: textbooks, calculators, dorm fridges, desk lamps, bicycles and clothing. A catalog, a product page, a cart, student accounts and a checkout, all pointing at one shared set of product records.

It is deliberately a small system with the same moving parts as a real store, because every part maps to something in the course: static pages, client scripting, server scripting and a database.

Two kinds of scripting, and which one runs now

Weeks 2 and 3 are the weeks the pages started reacting to people. Neither one touched the markup much: the same listings, the same design, a little more JavaScript each time.

Client-side, Weeks 2–3

The HTML files still arrive exactly as they are stored, and the server knows nothing about the change. js/filter.js, js/cart.js and js/register.js run in the browser, find elements on the page, and rewrite them as you type.

No request goes out, so results and error messages appear instantly. Turn scripting off and the catalog still loads, because the filter form still submits and reloads the page with the same values.

Server-side, Week 7 onward

PHP reads each request and queries MySQL, so listings come from a real table and the same URL serves every student differently.

Sign-in, sessions, a cart that survives a page reload and orders all appear once the data is live. Every check in js/register.js has to be repeated there, because a visitor can switch JavaScript off.

Still the same page

Filtering, cart totals and form validation are JavaScript behaviours, not new markup. js/ now holds five small files and register.html is the only page added.

The listing data stays in the HTML for now, which is why products.html carries the same eight listings it had in Week 1.

How each week adds to it

The same project across fourteen weeks, one topic at a time.

Weeks 1–2
Static catalog in HTML and CSS, then client scripting: live search, category and condition filters, sorting, and cart totals calculated in the browser.
Week 3
Events and form validation: addEventListener replaces the inline handlers, and a registration form checks required fields, formats and its own rules. This build.
Weeks 4–5
Animation, media and Web 2.0, then the rest of the interaction layer before the first assessment.
Week 6
CAT 1: the individual build is assessed and signed off before any team work starts.
Weeks 7–10
Server scripting and database: PHP pages, MySQL tables, registration, sign-in, sessions and a persistent cart.
Week 11
CAT 2: the merged team version is assessed against the full brief.
Weeks 12–14
Checkout, order management, seller tools, documentation and the final defence.

How the current pages are put together

Semantic HTML

One header, one nav, one main, one footer, one heading per page in order, and landmarks a screen reader can jump between.

One stylesheet

Colours, spacing and type sizes live as custom properties at the top of css/style.css, so a change there restyles every page.

Plain scripts

Five small files in js/, loaded at the end of <body>. No framework, no build step, no package manager, so the focus stays on the course material.

Open source

The code is public

Every page in this build is committed to GitHub as it is written, so the history shows the project growing week by week. In Week 7 this repository becomes the starting point for the team version.
